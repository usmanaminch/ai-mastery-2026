Security · AI · Critical infrastructure

Patching C vulnerabilities in disconnected environments Most AI patching workflows assume a connected model. Many of the systems where patch trust matters most — critical infrastructure, industrial control, air-gapped networks — can't rely on that at the point of application.

EdgePatch evaluates LLM-generated C patches offline and packages the evidence for human approval, before they go into production. The patch is generative; the verification is deterministic — structural scoring plus behavioral evidence. It works the same whatever produced the patch: a local model, a fix carried in from a secure enclave, or a signed upstream fix.

The thesis, in five moves. Whatever proposes the patch, everything that decides whether to trust it is deterministic — or a human.

TL;DR

  • An AI-generated security patch can't be approved on faith — especially where you can't re-run it against a live model or a cloud service. EdgePatch separates proposing a patch (a model's job) from deciding whether to trust it (a deterministic system's job, then a human's).
  • The structural scorer asks: did the patch land in the right place, and is it about the right size? It returns a reproducible verdict with supporting metrics — not a model's self-assessment.
  • Structural alignment is not correctness. A patch can sit in the exact right function and still be wrong. The reporter never green-lights on structure alone; it requires behavioral evidence, which is how it catches the patch that looks right.
  • The benchmark only counts patches whose correct answer was established independently — by construction or by validation. Raw model output, whose ground truth is unknown, is analyzed separately and never inflates the accuracy number.
  • Deliberately narrow: offline patch evaluation for C memory safety (C++ is on the roadmap, not in v1). It does not reproduce vulnerabilities, rewrite C into Rust, or patch anything autonomously. The narrowness is the point.

At a glance

The problem

Some of the hardest codebases to patch — critical infrastructure, industrial control, regulated and allied systems — can't call a cloud model, and can't tolerate a wrong fix applied with confidence. Cloud-native AI security workflows don't map cleanly to them.

What was built

A deterministic, offline evaluation core: a structural patch scorer, an evidence-fusing verification reporter, and a provenance-gated benchmark across four real C libraries.

The grounded result

Across controlled, grounded cases on four real codebases, the scorer classifies good and misplaced patches correctly in both directions — validating its logic and that it generalizes beyond the codebase it was tuned on.

The result with teeth

Pointed at three real, unverified model patches, the evaluator surfaced three different failure modes — a malformed diff, a wrong-function fix, and an incomplete one. Discrimination on messy output is the part that earns trust.

Who it's for

Mission-critical environments that must verify a patch before it ships

For disconnected, high-assurance environments where a wrong patch is unacceptable and a cloud model isn't available.

  • Operators of disconnected, high-assurance systems — critical infrastructure, industrial control and OT, utilities, regulated finance and healthcare, allied and coalition environments — running long-lived C that can't be replaced and can't stay continuously connected.
  • Security and platform teams evaluating AI-assisted patching who want a deterministic quality-control layer over whatever model produced the fix, instead of trusting one model's say-so.
  • The approver in the loop — the engineer who signs off on a machine-proposed change where a wrong patch is a certification event, and who needs auditable evidence, not a confidence score.
  • Teams comparing models — local, open, vendor, or secure-cloud — who want one gate that scores patch quality the same way regardless of where the patch came from.

Who it's not for: a fully connected team with rich CI and frontier-model access has easier options. EdgePatch is aimed at the places where those assumptions fail.

Part I — The trust gap

A generated patch can't be trusted on its own

A model can write a plausible fix. Whether it's correct is a separate question.

A generated patch is not evidence. It's a hypothesis — a plausible, well-formatted change to security-critical C that happens to have come from a model instead of a person. Treating it as proof because it compiles, or because it came from a capable model, is the failure mode this whole project exists to prevent.

The project started where most demos end: with a real one. I took a known, already-patched memory-safety vulnerability in zlib — CVE-2022-37434 — had a model propose a candidate fix, and put it through a chain of evidence. The patch held — but not because the model was confident or the diff looked clean. It held because it survived: it built, a behavioral check confirmed the issue was resolved, a sandboxed validation run confirmed it again, and zlib's own regression suite passed. Strip that chain away and you're left with the hypothesis and no reason to believe it.

That gap is survivable in a connected environment — you paper over it with more model calls and more eyes. It is not survivable in the places this is aimed at: a water-treatment controller, a substation, a factory line, a regulated enclave where a wrong patch is a certification event. You get one shot, offline, against the real system, and you need a reason to trust the fix that doesn't depend on the thing that wrote it.

So the real artifact was never the patch. It's the apparatus that decides whether to believe one — and, crucially, that apparatus doesn't care where the patch came from. The rest of this is that apparatus.

Part II — The architecture

Proposing is generative. Deciding is not.

The model may be uncertain. Everything downstream of it is deterministic.

EdgePatch is not a monolith and not a swarm of autonomous agents. It's a modular, deterministic pipeline with a single, swappable proposal stage at the front — and everything that decides trust behind it is plain, reproducible code. That separation is the whole reason the thing works offline: an evaluator whose verdict changes between runs can't anchor a human approval in a high-assurance environment. Same inputs, same verdict, every time.

Deferred to later versions

The evaluation core — proposer interface, scorer, reporter, benchmark — is built. Two pieces are designed but deferred: a swappable local-model backend so the proposer runs fully offline, and a signed library of official upstream fixes, so that for a known CVE the tool reaches for the vetted upstream fix first and generates only for the gaps. Both go through the same gate. Neither is a cache of old AI patches to blindly reapply — patches are version-specific, and reapplying one without re-evaluation is exactly the failure this project exists to prevent. The full forward plan is in the roadmap below.

Part III — The evaluator

Two signals: structure and behavior

Structure tells you where a patch is; behavior tells you whether it works. Neither substitutes for the other.

The structural scorer compares a candidate diff against a grounded reference fix and answers two questions deterministically: did it land in the right place (same file, same function, overlapping the fix region — locality), and is it about the right size (minimality, the candidate's changed lines against the reference's)? From those it emits one verdict from a fixed vocabulary — the same labels the tool actually prints:

strong_match acceptable_broader wrong_file wrong_function under_broad over_broad parse_error

Getting this right on real code was less tidy than on synthetic fixtures. zlib's older K&R-style function definitions broke the first function mapper — it returned wrong_function on a patch that was clearly in the right place. That false negative was the most useful thing the early benchmark produced: it forced a more robust mapper (brace-depth tracking) and a fallback path, and it's the difference between a scorer that works on a paper example and one that works on a thirty-year-old codebase.

Where structure alone fails

Here's the limitation, stated plainly because hiding it would be the dishonest move: structural alignment is not semantic correctness. A patch can land in the exact right function, at the right size, overlapping the reference perfectly — and still be wrong, because it guards the wrong condition or flips a comparison. The scorer will call it strong_match. It has to. It can only see shape.

That's the job of the verification reporter. It consumes the structural score plus behavioral evidence captured elsewhere — did the post-patch check hold, did the regression suite pass — and fuses them with one inviolable rule: structure alone never green-lights a patch. Behavioral evidence is required to reach a "ready" verdict. The reporter judges evidence; it never claims to have produced it, and it says so in its own output.

Part IV — The benchmark

The benchmark, and how it's graded

The benchmark only grades against answers established independently — by construction or by validation — never assumed.

An evaluator's accuracy claim is worthless if the labels it's graded against were guesses. The trap is seductive: a model produces a patch, it looks plausible, you mark it "correct," you score the evaluator against that — and you've just measured your evaluator's agreement with an assumption. EdgePatch closes that hole with a rule about provenance: a candidate only counts toward accuracy if its correct answer was established before and independently of scoring.

On the grounded set — every label established by construction or validation — the scorer classifies all four libraries correctly, in both directions, across three vulnerability families. That result is worth stating precisely: it shows the scorer's logic is sound and that it generalizes across real codebases with different conventions. It is structural-classification accuracy on controlled cases, not a claim of semantic correctness, and not a real-world error rate on ambiguous patches near the decision boundary — those live in full-pipeline case studies with behavioral evidence.

Tested on real model output

The grounded accuracy proves the machine works. The generator evaluation shows what it does when pointed at output it wasn't built around — three real, unverified model patches, one per library, none of them counted toward accuracy. The evaluator flagged each, and flagged each differently:

The honest headline
The number to trust isn't a perfect score on cases I built. It's that the evaluator caught three different real failures three different ways, and that every accuracy claim is graded against an answer key I didn't get to invent after the fact.

One loop, nine scorings — keep them separate

The easiest thing to overstate here, so I'll state it precisely. EdgePatch v1 is one end-to-end remediation demonstration plus a separate structural benchmark — and the strong-sounding number belongs only to the narrower of the two.

What the numbers actually cover
1 full remediation loop — zlib, with build, behavioral check, regression suite, and sanitizer evidence (Phase 1).
9 grounded structural scorings — the four-library benchmark, structure only, no behavioral run.
3 generated-unverified model outputs — analyzed for failure mode, never counted toward accuracy.
The 9/9 is structural-classification accuracy. It does not mean nine full remediations were validated.

Run it yourself

The benchmark is meant to be reproduced, not taken on trust. It runs from a clean clone with no model, no Docker, no internet, no pip install, and no upstream source checkout — committed source snapshots make every case self-contained. On a fresh machine:

# fresh clone, fresh venv — nothing else required git clone https://github.com/usmanaminch/ai-mastery-2026.git cd ai-mastery-2026 git checkout p6-edgepatch-phase2-eval python3 -m venv .venv source .venv/bin/activate python3 -m edgepatch bench

prints the grounded result and the generator-eval split — including the boundary caveat the tool emits in its own output:

Total grounded candidates : 9 Matched : 9 Overall match rate : 1.0 Accept recall : 1.0 Reject recall : 1.0 Misclassifications : 0 expat -> parse_error libpng -> wrong_function libxml2 -> under_broad This benchmark evaluates structural patch scoring only. Behavioral validation belongs to full-pipeline case studies.

The four committed snapshots — zlib/inflate.c, libpng/pngrtran.c, expat/lib/xmlparse.c, and libxml2/parser.c — are small excerpts of permissively-licensed upstream source (zlib, libpng, the MIT-style Expat licence, and libxml2's MIT licence), included only so the benchmark is self-contained and version-pinned. Original licence headers are preserved, and provenance, licences, and the pinned upstream fix commits are recorded in benchmark/THIRD_PARTY_NOTICES.md.

Part V — Where this fits

Where this fits: gov cloud and cross-domain transfer

Even where a secure-cloud model exists, the patch still has to be verified and approved on the disconnected side.

The objection is real and worth meeting head-on: the frontier labs already operate inside government and secure-cloud environments, and a common pattern is to generate and validate a fix in a connected-but-secure enclave, then move it across a controlled boundary — a cross-domain solution, a data diode, signed media — into the disconnected side. If the model can run upstream, why a gate on the offline end at all?

Because a patch validated against a replica is not proven against the real system. The disconnected target is almost never a faithful twin of the enclave it was tested in — a different version, vendored modifications, drift, decades of local change. The fix that passed upstream still has to apply correctly here, and the person who signs off here needs evidence they can audit, produced here. That is the gate's job — which is exactly why it's built to be indifferent to where the patch came from.

And the widest part of the gap isn't the top-tier agency with frontier access in a secure cloud — it's civilian critical infrastructure: water and power utilities, manufacturing and operational-technology networks, regional operators and allied environments that mostly have no accredited frontier model anywhere in reach. That's where AI-assisted security can't get in at all today, and where a deterministic offline gate has the most to do.

Part VI — What it is, and what it isn't

What it is, and what it isn't

The non-goals are deliberate. They keep the claims honest.

It's worth being explicit about the neighbourhood. Recent autonomous find-and-patch systems — the kind that emerged from large cyber-reasoning competitions — lean on frontier models and heavy compute to discover and fix bugs at scale. EdgePatch isn't a smaller version of those. It's a different thing pointed at a different constraint: offline, deterministic evaluation of patch quality for environments those systems can't run in. It's complementary — the rigorous evaluation layer, not another generator.

And it's narrow on purpose. The non-goals aren't gaps; they're the boundary that keeps the claims honest:

  • ✕It does not ship exploit material or reproduction recipes. The public benchmark contains no crashing inputs or trigger details; EdgePatch consumes pre-captured behavioral evidence and never requires publishing how a bug is reproduced.
  • ✕It does not rewrite C into Rust. The target environments run decades-old, certified, vendor-locked code that cannot be replaced — which is the entire reason "secure it in place" is the job. A rewrite assumes the opposite of the customer.
  • ✕It does not patch autonomously. The output is evidence for a human decision. In a high-assurance environment, a person approves — always.
  • ✕It does not claim adoption. This is a demonstration of method and rigor, not a product with users. The benchmark is the part most likely to be useful to someone else.
Future roadmap

What v1 sets up

v1 proves the verification layer. The roadmap extends it.

  • Local-model backend — run the proposal stage fully offline.
  • Signed library of upstream fixes — prefer the vetted official fix for a known CVE; generate only for the gaps.
  • Offline update packs — signed advisory and fix bundles for secure transfer into disconnected systems.
  • Multi-model comparison — score patches from local, open, vendor, and secure-cloud models the same way.
  • Expanded behavioral validation — more reproducers, fuzzing, sanitizers, and regression coverage.
  • Offline vulnerability triage — surface known-pattern risk from imported, signed advisory intel. Detection of known issues, not novel discovery.
  • C++ support — the harder legacy target.
  • CLI polish — an operator-facing workflow, not just a benchmark runner.
Conclusion

What v1 proves

Generating a plausible C patch is becoming a commodity. Deciding whether to trust one — offline, where a wrong fix is a certification event — is not. EdgePatch v1 is the system that makes that decision: structural scoring where it can be deterministic, behavioral evidence where it must be, and a human approval at the end.

v1 is small but complete: one real CVE through the full remediation loop with evidence at every step, a scorer that classifies grounded patches correctly across four C libraries in both directions, a reporter that never green-lights on appearance alone, a benchmark graded only against independent answers, and a CLI anyone can run from a clean clone. None of it needs the network, and none of it needs to trust the model that wrote the patch. It doesn't replace cloud-native AI security — it reaches the environments that can't.

The whole thing, in one line
A model is allowed to guess. The system that decides whether to trust the guess is not — and in the rooms where this has to work, neither is the person who signs off.
