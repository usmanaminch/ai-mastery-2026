# EdgePatch

### Air-Gapped, Exploit-Validated C/C++ Vulnerability Repair for the Edge

**Project P6**
**Author:** Usman Chaudhary
**Status:** Design specification (v0.1)
**Last updated:** June 10, 2026

---

## 1. Abstract

EdgePatch is an autonomous agent that discovers, validates, repairs, and verifies
memory-safety vulnerabilities in C/C++ source code while running entirely offline —
with zero network egress — on commodity server hardware inside an air gap. It produces,
for each finding, an auditable evidence bundle: a reproducible sanitizer crash that
proves the vulnerability is real, a minimal patch generated by a local code model, and
verification artifacts proving the crash is removed without breaking compilation or
existing behavior. Patches are proposed for human approval, never auto-applied.

The system targets a deployment niche that cloud-native AI security tooling cannot
serve by design: zero-egress environments — industrial control systems, OT networks,
and regulated financial and healthcare infrastructure — where the oldest and most
memory-unsafe codebases run, and where no external API may be called. These environments
are isolated, not under-resourced: they typically run racks of commodity server hardware.
The defining constraint is the network boundary, not the compute budget.

The engineering thesis is that locally-runnable models become effective at security
remediation when the surrounding system carries the deterministic load: static analysis
localizes the bug, fuzzing proves it, templates constrain the fix, and compilers and
sanitizers verify it. **The model does less because the system does more.**

---

## 2. Problem statement

AI-native vulnerability scanning has matured rapidly, but the production systems in the
category are cloud-native. They scan repositories using hosted frontier models, run
validation in cloud sandboxes, and return results over the network. This architecture is
sound for connected enterprises and structurally impossible for disconnected ones.

The environments that most need automated remediation are precisely the ones that
cannot use these tools:

- **Industrial control systems and SCADA** running decades-old C firmware.
- **Critical infrastructure** (power, water, transport) on isolated OT networks.
- **Regulated financial and healthcare systems** operating in zero-egress enclaves
  for compliance reasons.

These systems are written predominantly in memory-unsafe C/C++, carry large volumes
of legacy code, and are isolated from exactly the cloud services that could help them.
No AI-native scanner operates inside the air gap.

> **Scope note on positioning.** This project is framed around commercial and civilian
> air-gapped environments — critical infrastructure, ICS/SCADA, and regulated commercial
> enclaves. It is not positioned as a defense or classified-network deployment tool. The
> technical architecture is identical across those settings; the chosen focus is
> commercial critical infrastructure.

## 3. Design principles

1. **Evidence over assertion.** A finding is only surfaced if it can be reproduced as a
   sanitizer crash. No "potential" findings without runtime proof.
2. **Deterministic core, probabilistic edge.** Static analysis, fuzzing, compilation,
   and verification are deterministic. The model is invoked only where ambiguity
   genuinely requires it — narrow patch generation.
3. **Validation, not weaponization.** The system proves exploitability via crash
   evidence. It is architecturally incapable of producing a working exploit.
4. **Oversight by default.** The agent does the toil; a human approves the patch. Nothing
   is auto-merged.
5. **Auditable and reproducible.** Every run is seed-pinned, version-locked, and produces
   a signed evidence trail suitable for a regulated environment.
6. **Zero egress as the defining constraint.** The system makes no outbound network calls
   of any kind. Correctness is demonstrated under deny-all egress; the application has no
   cloud dependency regardless of where it runs.

---

## 4. Architecture overview

EdgePatch is a seven-stage pipeline. Stage 0 — build recovery — is the stage most
naive designs omit and the one most likely to sink a real-world target.

```
Stage 0  Build discovery       compile_commands.json, instrumentable target
Stage 1  Find (two-tier)        syntactic scan -> focused semantic taint analysis
Stage 2  Slice + harness        vulnerability slice (source->sink), fuzz harness
Stage 3  Validate (red team)    libFuzzer/AFL++ + ASan/UBSan -> reproduced crash
Stage 4  Patch                  template-first, model for narrow slices, critic
Stage 5  Verify (differential)  compile + static-gone + crash-gone + regression
Stage 6  Evidence report        before/after bundle, SARIF export, signed audit trail
```

A compute-aware scheduler sits across all stages, ranking candidate findings and
budgeting fuzzing and inference time. A phase-batched model orchestrator manages the
load/unload of the local LLM to fit edge memory limits.

## 5. Stage detail

### Stage 0 — Build discovery

For C/C++, compiling and instrumenting the target is frequently harder than the AI
work. Makefiles, Autotools, vendor headers, conditional macros, and cross-compilers all
stand between source and an instrumentable binary. EdgePatch attempts, in order: build
interception (`bear`), CMake compile-database export, and header inference. The success
criterion for this stage is not "can I read the files" but **"can I compile and
instrument the vulnerable target under sanitizers."** A target that cannot be built is
reported as such and excluded from dynamic validation rather than silently passed
downstream.

### Stage 1 — Find (two-tier)

A cheap syntactic pass (Tree-sitter queries, Semgrep rules, banned-API call-site
extraction) produces candidates quickly. A focused semantic pass (CodeQL local data
flow, or clang AST for typed information) runs **only on candidates**, tracing
source-to-sink taint to separate dangerous call sites from benign ones. Finding an
unsafe `strcpy` is trivial; proving the destination is too small and the source is
attacker-controlled is the real work, and it is reserved for the candidates that survive
tier one.

Each surviving candidate is emitted as a structured finding object (CWE, sink, source,
file, function, preconditions, slice, confidence, whether a harness is required).

### Stage 2 — Slice and harness synthesis

The context handed to the model is never a whole file. It is a **vulnerability slice**:
the attacker-input source, any sanitization or transformation along the path, the sink,
and the relevant buffer allocation or object lifetime. This slice is also what drives
harness synthesis — the generation of a `LLVMFuzzerTestOneInput` wrapper (for
function-level libFuzzer targets) or seed files and a stdin/file driver (for AFL++ on CLI
programs).

**Harness validation gate.** The synthesized harness is itself generated code and is
therefore an untrusted dependency. Before any verdict it produces is trusted, the
harness is instrumented with coverage and confirmed to **actually execute the vulnerable
sink line**. A harness that does not reach the sink is discarded, not run — this prevents
both false crashes (harness bug mistaken for target bug) and false negatives (sink never
exercised).

### Stage 3 — Validate (local exploitability validation)

This stage replaces the naive notion of an "LLM that writes exploits." Exploitation
requires deterministic precision that probabilistic models do not provide, and
weaponized exploit generation is an explicit non-goal. Instead, validation is an
orchestrator around coverage-guided fuzzing and sanitizers.

The agent is a state machine, not a free-form loop: classify finding → select strategy →
compile with sanitizers → generate seeds → fuzz under budget → triage crashes →
minimize reproducer → emit evidence. Strategy selection maps CWE classes to tooling
(ASan coverage fuzzing for overflows, UBSan boundary fuzzing for integer issues,
format-string mutation for CWE-134). Sandboxing uses nsjail or bubblewrap — Linux
namespaces, cgroups, seccomp, no network — both to contain crashes and to demonstrate
air-gapped operation.

The output is an exploitability verdict (`reproduced` / `not reproduced` /
`inconclusive`) plus an evidence bundle: crashing input, sanitizer trace, stack hash,
minimized reproducer, and a deterministic replay command. **Crash evidence, never a
weaponized payload.**

### Stage 4 — Patch

Patching is a planner → generator → critic pipeline, template-first.

The **planner** selects a remediation pattern from the finding's CWE (bounded copy with
null-termination for buffer overflows, constant format string for CWE-134, checked
arithmetic for integer overflow, and so on). The **generator** — the local quantized
model — is invoked only for the narrow slice, with a tightly constrained instruction:
*replace this unsafe copy with a bounded copy that preserves null termination and the
existing return signature; only edit lines X–Y; do not change the public API.* The
**critic** screens the output for the classic traps a small model falls into — for
example, a `strncpy` "fix" that compiles but silently fails to null-terminate.

Diffs are minimal by design. The system tracks lines changed, functions changed,
compilation status, test status, crash status, new warnings, and API compatibility.

### Stage 5 — Verify (differential)

Verification is layered and, critically, distinguishes **"the crash is removed"** from
**"the vulnerability is fixed"** — a distinction the obvious design collapses.

A fuzzer found *one* crashing input. A patch can fix that specific input while leaving
the vulnerability class open. To guard against masking rather than fixing:

- **Build verification** — compiles under the original flags, warnings-as-errors where
  feasible.
- **Static verification** — the original rule/query no longer fires.
- **Differential dynamic verification** — re-fuzz from the **same corpus plus fresh
  mutations under a new RNG seed**, not merely a replay of the one known input. The
  patch must hold against inputs it has never seen.
- **Sink-locality check** — confirm the patch lands at the sink (the write/copy), not
  merely rejecting one malformed input upstream.
- **Regression verification** — project tests plus a generated regression test built
  from the crashing input.

The system reports a **fix confidence** that is explicitly lower than the binary
"crash removed" signal, reflecting the genuine epistemic gap.

### Stage 6 — Evidence report

The deliverable is a before/after evidence bundle per finding: the reproduced crash and
sanitizer trace before, the minimal diff, and the verification results after.
Exported as SARIF for tooling interoperability and as a human-readable report. For
regulated-environment credibility the bundle is signed and carries an SBOM, the model
hash, the ruleset hash, the toolchain versions, and a complete offline audit trail with
no telemetry.

## 6. Cross-cutting systems concerns

### Demonstrating the air gap

The defining property of the system is zero network egress, and the proof is that the
application runs correctly with all outbound traffic denied. The reference demonstration
runs on a GCP VM with no external IP, in a VPC with no NAT gateway and egress firewall
rules denying all outbound connections. The full pipeline executes inside that isolation;
the firewall configuration and a network-activity trace showing zero outbound connections
are part of the evidence the project ships.

This is a stronger demonstration than a constrained edge device because it runs on
realistic server-class hardware (matching how disconnected environments are actually
provisioned) and proves the air gap with genuine cloud security controls rather than an
unplugged cable. The same property can be reproduced locally on any machine with
networking disabled or firewalled; where the code runs is irrelevant to the claim, which
is that the application has no egress dependency.

### Compute-aware scheduling

Disconnected server environments are isolated, not under-resourced, so exhaustive
analysis is usually affordable. The scheduler nonetheless ranks findings by expected
value, both to keep runs fast and to keep the design honest about prioritization:

```
risk_score = static_confidence
           x attack_surface_score
           x harnessability_score
           x patchability_score
           / estimated_compute_cost
```

High-value, low-cost findings are validated first.

### Hardware profile

The primary target is commodity x86-64 server hardware (the configuration real
disconnected environments run), with a GPU where available for local inference. The
reference deployment uses a standard GCP VM under deny-all egress. No special
quantization or memory-orchestration acrobatics are required at this scale; the local
model, compilers, fuzzers, and sandbox all coexist comfortably.

> **Optional edge profile (out of scope for MVP).** A genuinely constrained variant —
> for embedded or forward-deployed OT field devices — would reintroduce real compute
> limits (single-digit-GB RAM, CPU-only inference) and the corresponding engineering:
> phase-batched model load/unload, `llama.cpp` with ARM NEON, aggressive context
> budgeting. This is a legitimate but narrower scenario and is deferred. It is noted here
> as a future direction, not a current requirement.

Fuzzing is still budgeted (fast path ~30s, normal ~2–5 min, deep overnight), corpus and
crash retention are capped and deduplicated by stack hash.

## 7. Threat intelligence updates: the offline bundle channel

A disconnected defender that cannot benefit from the outside world's vulnerability
discoveries is fighting blind — especially now, as AI-driven discovery accelerates the
rate at which new vulnerabilities are published. EdgePatch stays current without ever
breaking the air gap, using the same controlled-transfer pattern that already governs
antivirus definitions and OS patches in classified and OT environments: **knowledge
flows in through signed offline bundles; nothing flows out.**

The architecture is deliberately two-sided, and only one side ever touches the network.

**Connected side (outside the enclave).** A pipeline with full network access watches CVE
feeds and public disclosures, and distills new intelligence into *detection artifacts*
rather than raw data: new static-analysis rules (Semgrep/CodeQL patterns for newly
disclosed bug classes), new or refined fuzzing harness templates, updated patch templates
for emerging patterns, and — when improved — a refreshed local model. Because this side is
not in the enclave, it can use any tooling, including frontier models, to produce these
artifacts.

**The boundary.** Artifacts are packaged into a **signed, versioned bundle**. The bundle is
the only thing that crosses, and it crosses through the same audited channel a regulated
environment already trusts — controlled media or a one-way data diode. Inside the enclave,
the bundle's signature is verified before anything is loaded. There is no live connection,
no callback, no telemetry. The data flow is strictly one-directional and asynchronous:
knowledge in, nothing out. The zero-egress property is fully preserved.

**The critical invariant: enrichment, not dependency.** The intelligence makes EdgePatch
*better at recognizing and fixing known patterns*, but the core find → prove → patch →
verify loop runs entirely self-contained and offline regardless. A freshly introduced
`strcpy` overflow is caught by structural analysis whether or not it appears in any feed.
The system functions fully disconnected with whatever bundle it last received; bundles
keep it current but are never required for it to operate. This is the line that keeps the
air-gap thesis intact — the system is offline-complete, and updates are batched
enrichments that arrive on the enclave's schedule, not a connectivity requirement.

What a bundle contains:

- Updated detection rules (new patterns for newly disclosed bug classes)
- New or refined fuzzing harness templates
- Updated patch templates for emerging patterns
- A refreshed local model, when improved
- Optionally, a curated CVE reference set — as benchmarking/pattern reference data, not a
  live feed

This connected-intel-to-disconnected-execution split is itself a piece of security
engineering that mirrors how regulated and classified environments actually stay current,
and it answers the obvious reviewer question — "how does an air-gapped tool avoid going
stale?" — with the real-world operational answer rather than a hand-wave.

## 8. Safety and dual-use posture

A system that autonomously finds memory-safety bugs and proves them exploitable is
dual-use: viewed from the other side, it is an autonomous vulnerability-discovery engine.
EdgePatch treats this as a first-class design concern rather than a footnote.

- **Validation, not weaponization** is a hard architectural boundary. The system produces
  sanitizer crashes and minimized reproducers; it does not produce shellcode, ROP chains,
  or payload delivery. This is a chosen constraint with a stated rationale.
- **Sealed artifacts.** Crashing inputs live in a sealed artifact store and are never
  emitted as runnable exploits.
- **Oversight by default.** Patches are proposed for human approval, never auto-merged.
  The agent automates the toil — discover, validate, draft, verify — and the human holds
  the gate.
- **A written threat model of the tool itself** ships with the project: what an adversary
  could do with it, and what is built in to prevent that.

This posture is not incidental to the project; it is part of the deliverable.

## 9. Interpretability probe

P6 folds in a mechanistic-interpretability component rather than running it as a separate
project. The concrete question: **what distinguishes the patch model's internal state
when it correctly recognizes a memory-safety bug from when it confidently hallucinates a
fix?**

The probe trains a lightweight linear classifier on the model's residual-stream
activations to predict whether a generated patch will pass verification — *before*
spending the compute to verify it. A working probe serves two ends: it is a practical
scheduling signal (skip low-confidence patches early) and a genuine research result, as
interpretability analysis of a quantized code model performing security remediation is,
to the author's knowledge, unexplored.

## 10. Scope (MVP)

| Dimension | MVP scope |
|---|---|
| Language | C first (defer broad C++; templates break AST matching) |
| CWE classes | CWE-120/121/122 (buffer overflow), CWE-787 (OOB write), CWE-134 (format string), CWE-190 (integer overflow) |
| Deferred | Use-after-free, double-free, heap grooming, ROP, races, deserialization |
| Validation | libFuzzer / AFL++ with ASan / UBSan |
| Patching | Template-first; local code model for narrow slices |
| Hardware | Commodity x86-64 server; reference deployment on GCP VM under deny-all egress |

Use-after-free and heap exploitation are deferred deliberately — they require stateful,
path-sensitive setups that small local models cannot orchestrate reliably, and chasing
them early makes the project look unfocused.

## 11. Evaluation

A three-layer benchmark, because synthetic data alone reads as academic:

- **Layer 1 — Juliet C/C++ 1.3 subset.** Controlled, CWE-labeled, instantly compilable
  good/bad pairs. Filtered to the MVP CWEs.
- **Layer 2 — Real CVE mini-suite.** 10–20 small, older C vulnerabilities from projects
  such as libpng, zlib, tcpdump, libxml2, sqlite — each with a vulnerable version, a
  patched version, a simple build, and a known reproducing input.
- **Layer 3 — Custom microbenchmarks.** 20–30 small vulnerable/fixed programs to exercise
  the loop before confronting real build-system chaos.

For real CVEs, the richer signal is not pass/fail but **comparison against the upstream
human patch** — a semantic diff between EdgePatch's fix and the official one.

The headline results table:

| Metric | Juliet subset | Real CVE subset |
|---|---|---|
| Static candidates found | x / y | x / y |
| Harness generated and sink-reaching | x / y | x / y |
| Crash reproduced | x / y | x / y |
| Patch generated | x / y | x / y |
| Patch compiled | x / y | x / y |
| Crash removed (differential) | x / y | x / y |
| Regression passed | x / y | x / y |
| Median runtime / finding | x min | x min |
| Peak RAM | x GB | x GB |

## 12. Novelty

Autonomous find-patch-verify is not itself new — DARPA's Cyber Grand Challenge
demonstrated machine-speed flaw reasoning and patching in 2016, and CodeQL and Semgrep
each already do parts of the static side well. EdgePatch's defensible contribution is the
**combination**:

1. **Air-gapped, zero-egress operation** — local model, local compilers, local fuzzers,
   reproducible with no outbound network of any kind, demonstrated under deny-all egress.
2. **Evidence-driven remediation** — `finding -> reproduced crash -> patch -> same crash
   gone (differentially)`, rather than findings-only or patches-without-proof.
3. **Compute-aware agentic scheduling** that ranks findings by expected value.
4. **Slice-constrained local patching** — local models made effective by giving them
   typed slices, sanitizer evidence, failing inputs, and strict diff budgets.
5. **Auditable security posture** — signed reports, SBOM, hashes, no telemetry — the
   product thinking a CISO background contributes and a pure ML engineer tends to omit.

The framing that matters: this is not an LLM replacing SAST. It is a constrained
autonomous system in which static analysis, fuzzing, local inference, and verification
cooperate to produce auditable security evidence in places cloud AI cannot go.

## 13. Proposed repository layout

```
edgepatch/
  build_probe/      detect build system, intercept, produce compile_commands.json
  scanner/          tree-sitter, semgrep, codeql runners, cwe rules
  slicer/           callgraph, taint trace, context packager
  validator/        harness synth, libfuzzer/afl runners, sanitizer triage,
                    crash minimizer, sandbox, harness coverage gate
  patcher/          planner, local llm client, patch templates, diff applier, critic
  verifier/         build / static / differential-dynamic / regression
  scheduler/        priority queue, compute budget, thermal monitor, phase orchestrator
  interp/           activation capture, verification-outcome probe
  safety/           threat model, artifact sealing, audit signer
  intel/            (connected side) cve feed watcher, rule distiller, bundle builder+signer
  updater/          (enclave side) bundle signature verify, rule/model loader
  reports/          evidence bundle, html report, sarif export
  bench/            juliet harness, cve suite, microbenchmarks, results
```

Note the `intel/` (connected) and `updater/` (enclave) split — these are the two sides of
the offline bundle channel and never share a process or a network path.

## 14. Open questions

- How far does CodeQL's local data-flow analysis scale before memory pressure on a
  single VM forces a fallback to clang-only typed AST?
- Can the interpretability probe generalize across CWE classes, or does each class need
  its own probe?
- What local model size gives usable patch quality on server-class hardware, and where
  is the quality/latency knee?
- For the differential verifier, what fuzzing budget on the post-patch re-fuzz gives a
  defensible "fix confidence" without dominating runtime?
